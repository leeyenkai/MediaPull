# Audit 2026-11-18, round 6

Round 5 was closed in commit 6ea1318. Three independent auditors read the code only: A network, engines and saving; B
library, Organise, analysis, windows; C what 1.8 added and the tests themselves. This round's brief added one rule: for
each round-5 closure, find every other path doing the same kind of action and check each one, and compare the stand-in
bridge with the real one event by event. Findings two auditors made are listed once, with both ids. Every finding was
checked against the code before it was fixed.

## Findings

### Major

| # | Finding | Closed by |
|---|---|---|
| A6-M1, C6-M1 | Scans and pulls into other folders overwrote the stored account id that folders from before 1.8 are compared with (made worse by round 5's early account event) | The id a name was first seen with is never replaced (`Store.updateAccount`). `testTheStoredAccountIDIsNeverReplaced` |

| A6-M3 | Saving an edited or trimmed copy of an item already saved did nothing: the S4-m2 skip took it for the item it was made from | A file on this Mac (an edit or trim) is never skipped. `--selftest-edit` "an edited copy of a saved item is saved" |
| B6-M1 | Undo and Redo made folders that had been renamed or trashed again at their old paths | Undo never makes a folder: other changes' records follow folders renamed or moved by later changes and by library folders followed after a Finder rename (`followFolderMoves`), and an item whose folder is gone stays where it is, to be put back later; Redo stops when its folder is gone and makes only folders inside it. `testUndoFollowsRenamedFoldersAndNeverRemakesThem`, `testRedoNeverRemakesAFolderThatWentAway` |
| C6-M2 | An Update without a record id did not follow a Finder rename once the store had followed it; Retry and Resume never gained the id | An Update gets its folder's record when queued; a pull's record id goes into its shared draft as soon as the folder has one (`PullRun.remember`); the store remembers former paths of Finder renames too. `testRecordsOfTrashedAndRenamedFolders` |
| C6-M3 | Downloads-form pulls used the save folder captured when queued: a rename before the job ran failed every file, and account details recreated the old folder | The save folder is followed by its bookmark when the job (or its Retry or Resume) starts, and the job stops when it is gone (`runPull`, `PullRun.rootBookmark`) |

## Why majors still appear

Four of the six majors were round-5 closures that missed a sibling path again (other routes that set the stored id, other
routes into an account folder, Undo and Redo beside `run`, form pulls beside updates). This round's brief made sibling
checking explicit, and the fixes were placed where all routes meet: one stored-id rule in the store, one owner check per
route of entry into a folder, one journal rule for run, undo and redo, records found by id with former paths. A6-M3 was
a regression from a round-4 shortcut whose assumption (an item's id fixes its content) did not hold for edits.
